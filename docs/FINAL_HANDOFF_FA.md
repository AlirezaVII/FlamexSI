# گزارش تحویل نهایی GitHub و وضعیت مسابقه — Falmex v6

**به‌روزرسانی:** این سند سابقهٔ تحویل پیشین است. تصمیم نهایی تیم برای گزارش جداگانهٔ A و B در [گزارش دومرجعی](DUAL_REFERENCE_FA.md) ثبت شده است.

## این آخرین بسته دقیقاً چیست؟

این بسته یک **به‌روزرسانی افزایشی repository** است، نه آپلود مجدد تمام پروژه و نه بستهٔ کامل داده‌های علمی. فایل‌های FLEX در همان مسیرهای اصلی repository قرار گرفته‌اند و بخش تازهٔ BASS-II زیر `bass-cv/` آمده است. راهنماها و گزارش وضعیت نیز در `docs/` قرار دارند.

- **۳۴۴ فایل `ADD`:** فایل‌های تازهٔ FLEX، کد و artifactهای سبک BASS-II و مستندات؛
- **۲۷ فایل `REPLACE`:** ۲۵ فایل تغییرکردهٔ FLEX، به‌علاوهٔ `README.md` و `.gitignore` ریشه؛
- **حذف فایل از repository اصلی:** صفر؛
- **فایل اجرایی build، cache یا وابستگی نصب‌شده:** در بسته قرار ندارد.

عملیات، اندازه و SHA-256 تک‌تک فایلها در `GITHUB_UPDATE_MANIFEST.json` ثبت شده است. برای اعمال، `docs/GITHUB_APPLY_GUIDE_FA.md` را دنبال کنید.

## بخش FLEX که اضافه یا اصلاح شده است

- ingestion واقعی PSI-69 و ثبت منبع/مجوز؛
- مسیرهای replication، time-series، compositional و uncertainty؛
- scientific review workspace، API و صفحهٔ review؛
- اسکریپت‌های اجرای discovery و بازبینی نتایج؛
- دادهٔ seed واقعی و findings قابل بررسی؛
- تست‌های ingestion، تحلیل و scientific review؛
- Dockerfile، PWA و اصلاحات لازم frontend/backend؛
- README جدید که وضعیت قدیمی «فقط synthetic» را حذف و نتایج و محدودیت‌های واقعی را ثبت می‌کند.

وضعیت علمی ثبت‌شده: ۲۷۴ آزمایش واقعی و ۴۴ خروجی اصلی؛ در split اصلی ۱۲ `validated`، ۳ `candidate`، ۲ `rejected` و ۲۷ `not_significant`. واژهٔ `validated` فقط وضعیت موتور آماری داخلی است، نه replication مستقل، اثبات علّی یا آمادگی عملیاتی.

## بخش BASS-II که به GitHub می‌رود

- کدهای آموزش، inference، ارزیابی، annotation، review و packaging؛
- مدل‌های سبک v4/v5/v6 و freeze recordها؛ مدل بزرگ v3 فقط در evidence کامل است؛
- Model Card، development comparison و نتیجهٔ per-frame کاندیدای نهایی v6؛
- selection و freeze مربوط به confirmation؛
- ۲۴ فریم منبع، annotation و mask مرجع اولیه؛
- هر ۹۶ mask پیش‌بینی freeze‌شدهٔ v3/v4/v5/v6؛
- metrics اصلی، نتایج per-frame، CSV مقایسه و نمودار؛
- maskهای دو بازبین، agreement، provenance، صف داوری و contact sheet؛
- پیش‌نویس فرم مسابقه و فایل وضعیت submission؛
- ابزار تازهٔ `finalize_adjudication_v6.py` برای اینکه بتوانید نتیجهٔ داور سوم را خودتان پردازش کنید؛
- `verify_lightweight_v6.py` برای کنترل یکپارچگی همین نسخهٔ سبک.

## چه چیزهایی عمداً داخل GitHub نیست؟

ویدئوهای خام، cache و فریم‌های development، foldها و fold predictionها، مدل‌های حجیم v2/v3، مجموعهٔ حجیم error/disagreement overlayها، دانلودهای ردشده، فایل‌های موقت و log شبکه، آرشیوهای اصلی بازبین‌ها و dependency/buildها داخل بسته نیستند.

بنابراین repository سبک برای بررسی کد، نمایش نتایج، کنترل hash و ارزیابی پس از داوری مناسب است؛ **برای بازتولید کامل آموزش یا inference روی ویدئوهای خام به‌تنهایی کافی نیست.** برای آن کار باید evidence کامل با SHA-256 زیر استفاده شود:

`cd957358eee42f5c0023c9b10114c65737ac2bb26a36b9127e48cdfbcb56bce3`

محدودهٔ بسته‌ها و hashهای دیگر در `docs/EVIDENCE.md` ثبت شده است.

## نتیجهٔ علمی که نباید پنهان یا زیبا جلوه داده شود

مدل نهایی v6 روی مرجع اولیهٔ confirmation در هر ۲۴ فریم **TP=0** دارد؛ FP برابر ۶۰٬۵۳۷ و FN برابر ۹٬۲۱۸ است. کاهش FP نسبت به نسخه‌های قبلی، این شکست segmentation را به موفقیت تبدیل نمی‌کند.

دو مجموعهٔ annotation واقعی پردازش شده‌اند، بدون ویرایش پاسخ هیچ بازبینی. A در ۷ فریم و B در ۲۴ فریم ناحیهٔ مثبت دارد؛ ۱۷ اختلاف visibility وجود دارد. Macro IoU اجتماع مثبت ۰٫۱۱۰۷۷۸ و Micro IoU برابر ۰٫۲۵۷۳۳۷ است. این اعداد توافق بین دو annotation را نشان می‌دهند، نه صحت علمی یا تایید متخصص.

**داوری سوم هر ۲۴ فریم هنوز انجام نشده است.** هیچ خروجی داوری سوم واقعی در بسته ساخته یا ادعا نشده است. اعتبار متخصص مستقل و operational readiness همچنان `false` است.

## آزمون‌هایی که واقعاً اجرا شده‌اند

- Backend روی سورس تغییرکردهٔ FLEX: **۹۶ تست موفق**؛
- Ruff روی backend: **موفق**؛
- Frontend با Node `v20.20.2`: ESLint، TypeScript و production build موفق؛ **۱۶ صفحهٔ static** ساخته شد؛
- بستهٔ کامل evidence قبلی: CRC موفق، verifier استخراج‌شده **۵۵/۵۵** و inference تکراری v6 pixel-identical؛
- verifier نسخهٔ سبک GitHub: **۱۳۲ بررسی موفق** برای منابع، ۹۶ پیش‌بینی، مدل‌های موجود و وضعیت بازبینی؛
- ابزار نهایی‌سازی داوری: اجرای سرتاسری روی ورودی آزمایشی، هم با JSON+PNG و هم JSON-only؛ هر ۹۶ پیش‌بینی بدون تغییر ارزیابی شدند.

ورودی داوری آزمایشی فقط برای test بوده، از بستهٔ علمی حذف شده و هیچ نتیجهٔ واقعی را جایگزین نکرده است. آرشیو اصلی آپلودشدهٔ repository نیز تغییر نکرده است.

## کارهای باقی‌مانده، به ترتیب انجام

۱. **داور سوم باید هر ۲۴ فریم را تکمیل کند.** فایل صحیح برای بازگشت، ۲۴ JSON تکمیل‌شده از بستهٔ `Falmex-داور-سوم-v6.zip` است. سبز/قرمز بودن overlay معیار خودکار درستی نیست.

۲. **مرجع داوری‌شده را freeze و همان پیش‌بینی‌ها را دوباره ارزیابی کنید.** راهنما و دستور در `bass-cv/README.md` آمده است. خروجی در مسیر تازه ساخته می‌شود و نتایج اولیه را بازنویسی نمی‌کند.

۳. **Model Card و فرم مسابقه را با نتیجهٔ واقعی پس از داوری به‌روز کنید.** اگر تخصص یا استقلال داور اثبات نشده است، عبارت «independent expert validation» را ننویسید. human review به‌خودی‌خود gold standard یا operational readiness نیست.

۴. **اطلاعات تیم و پرتال را وارد کنید:** نام تیم، اعضا، challenge/category، لینک عمومی repository، ویدئوی demo، لینک ارائه و هر فیلد اختصاصی پرتال. این موارد فعلاً در پیش‌نویس خالی/باز هستند.

۵. **تغییرات را بررسی، commit و push کنید** و آزمون‌های راهنما را روی نسخهٔ نهایی GitHub اجرا کنید. هیچ وب‌سایت یا deployment در این تحویل منتشر نشده است.

۶. ** evidence کامل را فقط از مسیر مجاز مسابقه یا Release ذخیره/پیوست کنید.** آن را به‌اشتباه به‌جای بستهٔ سبک داخل commit قرار ندهید و هیچ URL علامت‌دار یا credential موقت را منتشر نکنید.

## تصمیم فنی برای مرحلهٔ بعد

در این تحویل v7 آموزش داده نشده است. اگر بعد از داوری تصمیم به مدل جدید گرفته شود، استفاده از نتایج B14/B17/B18 برای tuning آن ویدئوها را به development منتقل می‌کند و باید ویدئوهای کاملاً تازه‌ای برای confirmation رزرو شوند. نباید همان confirmation مصرف‌شده دوباره «دیده‌نشده» معرفی شود.

## نقطهٔ شروع شما

اول `docs/GITHUB_APPLY_GUIDE_FA.md` را باز کنید و بسته را روی repository اعمال کنید. سپس پیش‌نویس مسابقه را از `bass-cv/submission-v6/` تکمیل کنید. تنها blocker علمی باز برای نسخهٔ نهایی، داوری سوم واقعی و به‌روزرسانی نتایج پس از آن است؛ بقیهٔ موارد عمداً اطلاعات تیم/پرتال یا پیوست‌های بزرگ هستند.
